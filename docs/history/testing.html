How Geth is tested

Proving Ground

Geth is tested in two layers. Unit tests check Geth's own code, in seconds, with no model at all. Benchmarks give real test deliveries to the agents, then score their plans against the known right answer. Every number on the Rannoch page comes from the second layer.

The two layers

Is Geth's code right? Are the agents right?

unit tests

Geth's code, without a model

Each test feeds a known input to one piece of Geth and checks the output exactly: the plan check, the run-time check against the approved plan, the report check, the agent loop. Most replay a real failure, so it cannot come back.

How many
88, in 4 files under geth/tests/
How long
under a second
Needs
nothing: no data, no model, no site settings
benchmarks

The agents, on real test deliveries

The planner gets a test delivery and a question, exactly as you would give them. Its plan is then scored, check by check, against the right answer for that delivery. Models make different mistakes from one run to the next, so each delivery is planned several times.

How many
15 deliveries, plus 9 sparse versions
How long
1 to 7 minutes per plan
Needs
the model service, the staged test data
Layer 1

Unit tests: every failure becomes a test

When something goes wrong in a real run or a benchmark, the fix comes with a test built from the real case: the same file names, the same wrong plan, the same error text. If a later change brings the failure back, the test says so.

Layer 2

One benchmark result, from delivery to score

The worked example is the 16S amplicon delivery: four soil samples, two control plots and two warmed plots, sequenced in two separate MiSeq runs.

  1. 1

    A test delivery that looks real

    Small public test data from nf-core, renamed the way a sequencing facility delivers it (1_S103_L001_R1_001.fastq.gz), with a README and a sample table written as a scientist would. The staging scripts in bench/ build them under testdata/; nothing about the right answer is in the folder.

  2. 2

    The planner plans, as for you

    bench/bench_plan.sh runs the normal geth plan with a fixed question, here "Which bacteria are in these soil samples? Compare the control and the warmed plots." Same skills, same tools, same plan check as a real analysis.

  3. 3

    The plan is scored against the truth

    bench/eval_plan.py knows the right design of each delivery and checks the plan files one point at a time. For 16S, 10 checks:

    pipeline is ampliseq4 rowsall samplesvalid namesdistinct namesR1/R2 pairsrunsprimers16S taxonomyno unknown options

    Qwen's plan r5qwen_ampliseq_16s_1 scored 9/10: it gave all four samples the same sequencing run, so the error model would be learnt across two runs. In red: the one that failed.

  4. 4

    One line per plan

    Each plan adds one line to $GETH_WORK_ROOT/geth/bench/<tag>.jsonl. A plan counts as fully correct only if every check passes, Geth's own plan check accepts it, and planning did not fail. Below, Sol's line for the same delivery, which asked about the runs and scored 10/10.

Testing a planner that asks

Sparse deliveries and a stand-in scientist

A planner that asks questions needs someone to answer them, and nobody can sit through 90 plans. So each sparse delivery comes with a stand-in.

  • A sparse delivery keeps the same reads and reference, but its README is one line, for example "16S rRNA amplicon sequencing of soil samples, Illumina MiSeq paired-end." The files are hard links, so they take no extra space and are visible inside the agent sandbox.
  • The facts it no longer says move to bench/facts/<delivery>.txt, written as the scientist would know them: primers, plots, runs, controls.
  • The stand-in is a separate model call (Qwen) that answers only from that file, copying exact values, and answers "I don't know: use your recommendation" otherwise. It never sees the scorer's truth.

What are the forward and reverse primer sequences used for the 16S rRNA amplification?

515F (GTGYCAGCMGCCGCGGTAA) and 806R (GGACTACNVGGGTWTCTAAT).

Are there any negative controls included in this run that should be marked for decontamination?

I don't know: use your recommendation.

Each sparse delivery is then planned three ways: without questions, asking the stand-in, and with the full README. The difference between the first two is what asking is worth (3/18 against 15/18 fully correct in R3). The third shows that a planner which asks does not get worse when the README is complete.

Tuned and held out

After the first round, the skills were improved using 6 sparse deliveries. To check that this was not just fitting the test, 3 more sparse deliveries were held out and never used for tuning: Nanopore barcodes, ATAC-seq and Iso-Seq. Their scores (8/9 against 6/9 without questions) are the honest measure.

Comparing models

Only the model may differ

For Qwen, GPT-6 Luna and GPT-6.1 Sol, everything else was held the same, so differences in the scores belong to the planner's model.

  • Same deliveries, question, skills, tools and plan check; same number of plans (27 sparse, 18 full).
  • Same stand-in for all: always Qwen, whatever model plans. A better stand-in for one model would flatter it.
  • Same code: the Qwen side was rerun with the day's planner, not taken from older runs.
  • Paid models only within hard budgets: each plan stops at its cap, and the benchmark starts no plan once its total is spent. Both were tested on Qwen with made-up prices before any paid call.
Before a new check goes in

Replay it on every past plan

A new check or warning is first run over all the plans in the runs folder, 477 by now. It must flag only plans that really were wrong. A check that fires on good plans would teach you to ignore it.

Limits

What the tests cannot tell you

Small numbers

3 plans per delivery shows a trend, not a precise rate. A difference of one or two plans (43/45 against 45/45) is within noise.

The truth can be wrong

The scorer trusts what I wrote about each delivery. Twice it was wrong: two READMEs claimed 50 bp reads that are 76 bp, and the planner that measured the reads was marked wrong.

The stand-in makes mistakes

With its thinking off it once gave a wrong replicate grouping, and the planner followed it. Such misses belong to the stand-in, not the planner.

Real deliveries find more

No benchmark had multiplexed 10x data until your chicken delivery. The next step records what you change in a plan before approving it, so each real use can become a test.

Commands

Running a benchmark yourself

# stage the test deliveries (once)
bash bench/stage_deliveries.sh          # ChIP, ATAC, 16S, Nanopore, ancient DNA, Iso-Seq, ...
bash bench/stage_sparse.sh              # their sparse versions

# 3 plans of 2 deliveries, Rannoch planner, scored as they finish
GETH_PLANNER=harness bash bench/bench_plan.sh mytag 3 bulk_yeast ampliseq_16s

# sparse versions, with the stand-in answering from bench/facts/
GETH_PLANNER=harness GETH_BENCH_TESTDATA=testdata_sparse GETH_BENCH_ANSWERS=yes \
    bash bench/bench_plan.sh mytag_sparse 3 ampliseq_16s

# results: one JSON line per plan
cat $GETH_WORK_ROOT/geth/bench/mytag.jsonl

Full runs, where an approved plan is run through the pipeline and its report checked, use bench/bench_run.sh and bench/eval_run.py the same way.
